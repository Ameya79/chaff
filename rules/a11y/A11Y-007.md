## Context & Problem
A classic tell of uncrafted code is attaching `onClick` event listeners to non-semantic container elements (`<div onClick={...}>` or `<span onClick={...}>`) styled with `cursor: pointer`. Non-interactive elements do not appear in the tab navigation sequence, cannot be focused by keyboard users, and do not trigger on standard `Enter` or `Space` keypresses. Attempting to fix this by adding a positive `tabIndex={1}` or `tabIndex={2}` is an anti-pattern that scrambles the natural reading and navigation order of the page, causing focus jumps across unrelated parts of the screen.

## Detection Logic
Static AST analysis searches for:
1. `onClick` handlers attached to non-interactive HTML tags (`div`, `span`, `p`, `section`, `article`, `li`) without an accompanying `role="button"` and `onKeyDown` handler.
2. Any `tabIndex` attribute with a value greater than `0`.

## Remediation Steps
1. Replace clickable non-interactive containers with semantic interactive elements: use `<button type="button">` for actionable triggers and `<a href="...">` for navigational links.
2. Restrict `tabIndex` values strictly to `0` (adding a custom element to natural focus order) or `-1` (enabling programmatic focus via script without adding to tab order). Never use positive tabindex values (`tabIndex > 0`).
3. If a custom widget requires a non-standard tag, declare `role="button"`, `tabIndex={0}`, and implement an `onKeyDown` handler that intercepts `Enter` and `Space` keys (`e.key === 'Enter' || e.key === ' '`).
4. Ensure disabled buttons declare the native `disabled` attribute rather than merely styling classes.

## Verification
Automated axe-core audit inspecting `tabindex` and `nested-interactive`. Navigate the entire user interface using only `Tab`, `Shift+Tab`, `Enter`, and `Space`. Verify that every actionable feature can be fully triggered without touching a mouse.
