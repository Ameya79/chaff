## Context & Problem
AI-generated form layouts frequently omit proper `<label>` elements, instead placing an unassociated `<span>` or `<p>` tag above the input, or relying entirely on an `input placeholder="Enter email"` attribute. Placeholders disappear the moment a user begins typing, provide inadequate contrast, and are not reliably announced as labels by screen readers. When labels are not programmatically connected to their inputs via `htmlFor` and `id`, screen readers announce the input simply as "edit text, blank", leaving users unaware of what data is expected. Furthermore, clicking the label text fails to focus the input.

## Detection Logic
Static AST analysis inspects all form input elements (`<input>`, `<select>`, `<textarea>`) and verifies:
1. The element is wrapped directly inside an enclosing `<label>` element; OR
2. The element possesses an `id` that matches the `htmlFor` attribute of a `<label>` element; OR
3. The element possesses an explicit `aria-label` or `aria-labelledby` attribute.
Flags any form input lacking an accessible programmatic label association.

## Remediation Steps
1. Pair every form control with an explicit `<label htmlFor="field-id">` matching the input's `id="field-id"`.
2. Connect supporting helper text, formatting instructions, or error messages to the input using `aria-describedby="field-hint"`.
3. If visual design explicitly forbids a visible text label (such as a compact search bar in a header), provide an accessible name via `aria-label="Search site"` or embed `<label htmlFor="search" className="sr-only">Search site</label>`.
4. Never substitute `placeholder` for a proper `<label>`.

## Verification
Run axe-core automated audit inspecting `label` and `form-field-multiple-labels`. In the browser, click on every form label text to confirm that focus immediately transfers to the corresponding input element.
