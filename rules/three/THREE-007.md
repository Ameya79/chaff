## Context & Problem
3D assets generated by CAD packages or digital content creation tools commonly contain millions of uncompressed vertices, multiple 4K texture maps, and duplicated material definitions. When exported as raw OBJ or uncompressed GLTF/GLB files, payloads easily reach 10 MB to 50 MB. Shipping massive 3D models into web hero sections overwhelms mobile cellular connections, stalls asset streaming, and leads to unacceptable page abandonment rates. Clause 5 of the Chaff Fallback Contract establishes a strict performance budget: the combined initial 3D JavaScript chunk plus initial 3D geometry payload must remain strictly under 250 KB gzipped.

## Detection Logic
Static build artifact inspection and network payload analysis verify:
1. Total gzipped transfer size of the dynamic 3D code chunk plus initial `.glb`/`.gltf` model file.
2. Presence of uncompressed 3D model formats (`.obj`, `.fbx`, `.dae`, or uncompressed `.gltf`).
3. Absence of Draco or Meshopt geometry compression in production 3D asset pipelines.

## Remediation Steps
1. Compress 3D geometry using Google Draco or Meshopt compression via `gltf-transform`:
   ```bash
   npx gltf-transform draco input.glb output.glb --quantize-position 14
   ```
2. Downscale initial hero textures to WebP or KTX2 formats with maximum dimensions of 1024x1024 pixels.
3. Tree-shake Three.js imports by importing only required modules instead of the monolithic `import * as THREE from 'three'`.
4. Defer secondary textures, environment maps (HDR/EXR), and background meshes, loading them asynchronously only after user interaction.

## Verification
1. Run a production build (`npm run build`) and inspect bundle output.
2. Assert that the isolated 3D bundle chunk is under 150 KB gzipped and the initial compressed GLB model is under 100 KB gzipped, satisfying the total <= 250 KB gzipped Fallback Contract threshold.
3. Confirm network transfer size in browser DevTools network panel with gzip compression enabled.
